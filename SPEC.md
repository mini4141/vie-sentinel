# Sentinel: specification

Read `CLAUDE.md` first for guardrails. This file defines WHAT to build and in WHAT ORDER.

## 1. Purpose and philosophy

Sentinel is a portfolio project that shows a Backend Engineer (Fraud domain) can design, build, containerise, test, provision and deploy a JVM service on AWS using Terraform and GitHub Actions.

**Priority: breadth and correctness of the TECH STACK over depth of business logic.**

- Every technology below must be demonstrably working end to end.
- Business logic stays deliberately small. Do NOT add edge-case handling, extra rules, or extra endpoints beyond this spec.
- Testing target: a few meaningful unit tests, one integration test, and ONE end-to-end smoke test of the common success flow that runs identically against local Docker, CI and AWS. No exhaustive edge-case suites. No coverage percentage target.
- When in doubt, cut scope, not quality of the infrastructure parts.

## 2. Tech showcase checklist (the real deliverable)

Each item must be demonstrable in the repo, and the README must link to the evidence.

| # | Skill to show | Evidence |
|---|---|---|
| 1 | Kotlin + Spring Boot 3 service | `app/` |
| 2 | Relational DB (Postgres) with migrations | Flyway files, repository layer |
| 3 | Async messaging (SQS) | queue + DLQ, worker consuming, same code path locally via LocalStack |
| 4 | Docker | multi-stage Dockerfile, non-root user, `docker-compose.yml` for the full local stack |
| 5 | CI with GitHub Actions | `ci.yml` passing: build, test, detekt, image build, compose smoke test |
| 6 | Infrastructure as code (Terraform) | modular, remote state, `fmt`/`validate` in CI, `plan` on PR |
| 7 | AWS: VPC, ALB, ECS Fargate, RDS, SQS, ECR, Secrets Manager, CloudWatch, SNS | applied once, proof captured |
| 8 | CD via GitHub OIDC (no static keys) | `deploy.yml` and `destroy.yml` via `workflow_dispatch` |
| 9 | Observability | JSON logs, Micrometer metrics, one CloudWatch dashboard, 2 alarms |
| 10 | Cost discipline | ephemeral stack, teardown verified, Cost Explorer screenshot |
| 11 | AI-assisted workflow | `CLAUDE.md`, `docs/AI_WORKFLOW.md` |

## 3. Local-first rule

AWS is touched ONLY after Phases 1-4 are fully green locally. Planning against AWS (`terraform plan`) is free and allowed in Phase 4. `terraform apply` is allowed only in Phase 5 and later.

## 4. Phases and acceptance gates

Do the phases in order. Do not start a phase until the previous gate passes. After each phase, commit and update `docs/AI_WORKFLOW.md`.

### Phase 1: Core service (local, no Docker for the app yet)
Build:
- Spring Boot 3, Kotlin, Gradle Kotlin DSL, Java 21. Package root `dev.sentinel` with sub-packages `api`, `rules`, `engine`, `persistence`, `queue`.
- Postgres via Docker Compose (only the DB for now) and Flyway migrations for the data model in section 5.
- API per section 6, API-key protected.
- The three rules in section 7 plus the scoring engine.
- Actuator `/actuator/health` and Prometheus metrics.
Gate:
- `./gradlew test` passes.
- App runs with `./gradlew bootRun` and a manual `curl` to `POST /events` returns a decision.

### Phase 2: Docker and async path (local)
Build:
- Multi-stage `Dockerfile` (build with Gradle, run on a slim JRE image, non-root user, healthcheck).
- `docker-compose.yml` with services: `app`, `postgres`, `localstack` (SQS only). Queue and DLQ created on startup by an init script.
- SQS integration: on `REVIEW` or `BLOCK`, publish a message. A listener in the same app (profile `worker` or same process, whichever is simpler) consumes it and writes a row to `alerts` and increments a metric. Endpoint and region overrides come from config so the SAME code runs against LocalStack and real SQS.
- `scripts/smoke-test.sh BASE_URL` (see section 8).
Gate:
- `docker compose up --build -d` then `scripts/smoke-test.sh http://localhost:8080` exits 0.

### Phase 3: CI (GitHub Actions)
Build `.github/workflows/ci.yml`, triggered on push and PR:
1. Set up JDK 21 and Gradle cache.
2. `./gradlew detekt test`.
3. Build the Docker image.
4. Run compose and `scripts/smoke-test.sh` against it.
5. Upload test reports as artifacts.
Gate: workflow is green on `main`, and a README badge is added.

### Phase 4: Terraform (validate and plan only)
Structure per `CLAUDE.md`: `infra/bootstrap/`, `infra/demo/`, shared `infra/modules/`.
Modules: `network`, `ecr`, `rds`, `sqs`, `ecs_service` (cluster, task def, service, ALB, target group, security groups, log group), `monitoring` (dashboard, alarms, SNS), `oidc` (GitHub OIDC provider and deploy role, restricted to this repo and `main`).
Requirements:
- Variables with sensible defaults, outputs for the ALB DNS name and queue URL.
- DB password generated by Terraform and stored in Secrets Manager. API key stored in Secrets Manager. ECS task reads both as secrets, never in plain env vars.
- Tags on all resources, per `CLAUDE.md`.
- Remote state in S3 with DynamoDB locking for `demo`; `bootstrap` may use local state, committed encrypted-free (no secrets) or ignored, whichever is simpler.
- `terraform fmt -check` and `terraform validate` run in CI. A `terraform-plan.yml` runs `plan` on PRs via OIDC and comments the output.
Gate: `terraform validate` passes for both stacks, and `terraform plan` for `demo` shows a sensible resource count with no banned resources from `CLAUDE.md`. Show the plan to the user and wait for approval before Phase 5.

### Phase 5: Deploy, prove, destroy (first AWS spend)
Follow the "Demo run procedure" in `CLAUDE.md` exactly.
1. Apply `infra/bootstrap/` (state bucket, lock table, ECR, OIDC role).
2. Build and push the image to ECR.
3. Apply `infra/demo/`, start the kill timer.
4. Run `scripts/smoke-test.sh http://<alb-dns>`. It must exit 0.
5. Save proof into `docs/proof/` (section 9).
6. Destroy `infra/demo/`, run `scripts/verify-teardown.ps1`.
Gate: smoke test passed on AWS, proof saved, teardown verified clean.

### Phase 6: CD via GitHub Actions (second short AWS session)
Build:
- `deploy.yml` (`workflow_dispatch`): OIDC login, build and push image, `terraform apply` for `demo`, run smoke test against the ALB, upload proof as an artifact, and ALWAYS run the destroy job at the end (use `if: always()`), followed by the teardown check.
- `destroy.yml` (`workflow_dispatch`): manual emergency teardown.
Gate: one successful `deploy.yml` run that ends with a clean destroy. Link the run in the README. Total uptime again under 1 hour.
Note: if the user says time or budget is short, Phase 6 may be skipped and Phase 5 evidence alone is acceptable; record this in the README.

### Phase 7: Documentation and polish
- `README.md`: one-paragraph pitch, architecture diagram (Mermaid), the tech showcase table with links, how to run locally in 3 commands, how the ephemeral deploy works, GCP-to-AWS mapping table, cost summary, proof gallery.
- `docs/adr/`: 3 short ADRs (why SQS, why Fargate over EC2 or Lambda, why ephemeral environment and no NAT).
- `docs/AI_WORKFLOW.md`: what was delegated to AI, what was reviewed, what was changed by hand, what went wrong.
- `docs/runbook.md`: deploy, rollback, teardown, and "what to do if the kill timer fails".

## 4a. Resource choices (recommended defaults, not strict)

These are starting points chosen for a cheap, short-lived demo (about $0.11 per hour). Use them unless real evidence during development shows they are insufficient. Switching is allowed under the escalation rule at the end of this section.

**Local (Docker Compose)**
- App base image: `eclipse-temurin:21-jre` (or the `-alpine` variant if it works). Build stage: `gradle:8-jdk21` or the Gradle wrapper.
- Postgres: `postgres:16`. LocalStack: current `localstack/localstack` image with only `SERVICES=sqs`.
- JVM flags: `-XX:MaxRAMPercentage=75 -XX:+UseSerialGC` (small containers). Spring Boot 3.x, Spring Cloud AWS 3.x for SQS.

**AWS (region `ap-southeast-1`)**

| Component | Recommended default | Notes and fallback |
|---|---|---|
| ECS task (Fargate) | 0.5 vCPU / 1 GB, Linux x86_64 | Avoid 0.25 vCPU / 0.5 GB, too small for Spring Boot. Fallback: 1 vCPU / 2 GB. ARM64 is about 20% cheaper but needs multi-arch image builds, so only choose it if time allows. |
| ECS service | 1 task, no autoscaling, health check grace period 120 s | Deployment min healthy 0 / max 100 percent for fast replacement |
| ALB | 1 internet-facing ALB, 2 AZs (required), HTTP:80, health check on `/actuator/health` | No HTTPS or domain |
| RDS | PostgreSQL 16, `db.t4g.micro`, single-AZ, 20 GB gp3, `publicly_accessible = false`, backup retention 0, no Performance Insights, `skip_final_snapshot = true`, `deletion_protection = false` | Fallback: `db.t4g.small` if CPU credits or memory run out |
| Network | 1 VPC, 2 public subnets across 2 AZs, internet gateway, no NAT, no private subnets | ECS tasks get a public IP so they can reach ECR, Secrets Manager and SQS without a NAT. RDS accepts connections only from the ECS security group. ALB accepts HTTP from anywhere, ECS accepts only from the ALB. |
| SQS | 1 standard queue plus 1 DLQ, `maxReceiveCount = 3`, retention 1 day | |
| Secrets Manager | 2 secrets (DB password, API key), `recovery_window_in_days = 0` | |
| ECR | 1 repository, lifecycle keeps last 3 images, scan on push optional | Lives in the bootstrap stack |
| CloudWatch | Log retention 3 days, 1 dashboard, 2 alarms (ALB 5xx, DLQ not empty), SNS email topic | |
| Terraform | Terraform 1.x, AWS provider `~> 5.0` or newer major if it works | Pin versions in `.terraform.lock.hcl` and commit it |
| State | S3 bucket (versioned, encrypted) plus on-demand DynamoDB lock table | Both live in the bootstrap stack |
| GitHub Actions | `ubuntu-latest` runners, `actions/setup-java` Temurin 21, `aws-actions/configure-aws-credentials` with OIDC | |

**Escalation rule**
- If evidence shows a default is not enough (OOM kill, task restart loop, health check failures from slow startup, DB CPU or connection exhaustion), step up ONE size (for example Fargate 1 vCPU / 2 GB, or `db.t4g.small`).
- First try cheap fixes: JVM flags, connection pool size, lazy initialisation, a longer health check grace period.
- Record the evidence and the change in `docs/adr/`, and tell the user the new approximate hourly cost.
- The hard bans in `CLAUDE.md` still apply. Sizing flexibility never covers NAT, Multi-AZ, EC2 and the other banned resources.

## 5. Data model (Flyway V1)

- `events`: `id` uuid PK, `idempotency_key` text UNIQUE, `user_id` text, `device_id` text, `ip` text, `type` text (`INSTALL`, `OFFER_COMPLETED`, `REDEEM`), `amount` numeric null, `play_seconds` int null, `occurred_at` timestamptz, `decision` text, `score` int, `reasons` jsonb, `created_at` timestamptz. Indexes on `(user_id, occurred_at)` and `(device_id)`.
- `rules`: `id` text PK (rule key), `enabled` bool, `shadow` bool, `params` jsonb, `updated_at`.
- `cases`: `id` uuid PK, `event_id` FK, `status` (`OPEN`, `APPROVED`, `REJECTED`), `created_at`, `resolved_at`.
- `rule_audit`: `id` bigserial, `rule_id`, `changed_by` text (from API key owner or header `X-Actor`), `change` jsonb, `at`.
- `alerts`: `id` bigserial, `event_id`, `decision`, `created_at` (written by the queue consumer).
Seed `rules` with the three rules in section 7.

## 6. API (keep exactly this surface)

All endpoints except health require header `X-API-Key`.

- `POST /events`: body `{idempotencyKey, userId, deviceId, ip, type, amount?, playSeconds?, occurredAt}`. Returns `{eventId, decision, score, reasons[]}`. Re-posting the same `idempotencyKey` returns the original decision and creates no new row.
- `GET /cases?status=OPEN`: list cases.
- `POST /cases/{id}/resolve`: body `{status: APPROVED|REJECTED}`.
- `GET /rules`: list rules.
- `PUT /rules/{id}`: body `{enabled, shadow, params}`. Writes an audit row.
- `GET /actuator/health` (public) and `/actuator/prometheus`.

Validation: basic bean validation only (required fields). No further input hardening.

## 7. Rules and scoring (deliberately simple)

Each rule implements `Rule { fun evaluate(event, ctx): RuleResult(score, reason?) }`. Rules in `shadow` mode are evaluated and recorded in `reasons` with a `[shadow]` prefix but add 0 to the score.

1. `velocity`: more than `maxEvents` (default 5) events from the same `userId` in `windowSeconds` (default 60) gives +50.
2. `device_sharing`: more than `maxUsers` (default 3) distinct `userId`s seen on the same `deviceId` gives +40.
3. `fast_completion`: `OFFER_COMPLETED` with `playSeconds` below `minSeconds` (default 10) gives +60.

Decision: total score >= 80 gives `BLOCK`, >= 40 gives `REVIEW`, otherwise `ALLOW`. `REVIEW` creates an `OPEN` case. `REVIEW` and `BLOCK` publish an SQS message. Thresholds are config values.

## 8. Testing strategy (intentionally light)

- **Unit tests:** 1-2 tests per rule (triggers, does not trigger) and 2 for the engine thresholds. No more.
- **One integration test:** Spring context plus Testcontainers Postgres, posting one event and asserting the stored decision. Skip it if Docker is unavailable on the machine.
- **Smoke test `scripts/smoke-test.sh BASE_URL`** (bash with curl, runs in CI and Git Bash; fail on any non-expected result). Flow:
  1. `GET /actuator/health` is `UP`.
  2. `POST /events` for a normal user returns `ALLOW`.
  3. Send a burst of events for one user above the velocity limit; the last returns `REVIEW` or `BLOCK`.
  4. Replay one `idempotencyKey`; the same `eventId` comes back.
  5. `GET /cases?status=OPEN` contains a case.
  6. `POST /cases/{id}/resolve` returns success.
  7. `PUT /rules/velocity` with `shadow: true` returns success, and the audit row exists.
  8. Poll for up to 30 seconds until the SQS consumer has produced an `alerts` entry (exposed via the `sentinel_alerts_total` metric on `/actuator/prometheus`).
  Print a clear PASS or FAIL summary with timings.
- Same script is the proof for local, CI and AWS. API key passed via `API_KEY` env var.
- NOT required: edge cases, load tests, security tests, coverage thresholds.

## 9. Proof artifacts (saved in `docs/proof/`)

- `smoke-test-aws.txt`: full console output with timestamps, including the ALB DNS name.
- `terraform-apply.txt` and `terraform-destroy.txt`: trimmed output.
- `verify-teardown.txt`: shows zero leftover resources.
- Screenshots (the user captures these; ask when ready): ECS service running, RDS available, CloudWatch dashboard with traffic, GitHub Actions green run, Cost Explorer showing the small total.
- Optional: 30-60 second screen recording.
Keep AWS account IDs out of public files: redact them in screenshots and text before publishing.

## 10. Non-goals (do not build)

Authentication beyond one API key, user management, a UI, multi-region, autoscaling, HTTPS or custom domain (ALB DNS over HTTP is fine for the demo), blue/green deploys, caching, extra rules, ML models, Kubernetes.
